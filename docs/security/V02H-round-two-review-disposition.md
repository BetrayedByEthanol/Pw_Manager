## The two owner qualifications (binding to this findings acceptance)

**Q1 — F-1 remains an owner-controlled Standard recovery choice, not automatically a defect or a prohibition.** A separately sealed `CodeOnly` entry-DEK recovery envelope can be structurally valid in a password-only vault even when a Standard entry's *normal* mode requires a custom password or hardware. This **weakens the effective recovery assurance** and requires an explicit informed **owner decision before provisioning** (`OPEN-REC-CONSENT`), per-entry affected-path reporting, Option A code collection, and no implicit weak slot, no preselected downgrade and no silent `STRICT_NONE` default. **Code-only VMK recovery alone does not unlock VERS or all Standard DEKs**. ISOLATED normal access and every complete DEK route remain hardware-mandatory; recovery may instead be `STRICT_NONE`.

**Q2 — Neither V02-B HMAC/P6 nor V3RV cross-language tests establish cryptographic security.** V02-B checks a derived HMAC before AEAD decryption; P6 rejects a specific AEAD-valid ciphertext forgery without the corresponding commitment key. That is **one negative test**, not a proof of multi-key commitment, adversarial factor independence, partitioning-oracle resistance or a tight `2^-256` bound. V3RV currently has **no authenticated seal/open, verified MAC or vNext KEK schedule**. Its two-language vectors establish canonical untrusted **framing and context bytes only**. Require a formally stated commitment security game, attack/assumption analysis and a named qualified OPEN-01 review of the eventual authenticated protocol; separate real hardware OPEN-15 evidence is required.

## Additional W1/probe observations — accepted as limitations, not blanket defect claims

| Observation | Scope / review disposition |
| --- | --- |
| **Cross-slot ancestry** | Pairs of separately valid `V3RV` descriptors may form cycles, dangling references, duplicated IDs and unauthorized group/credential scopes. Python's graph model is **not** enforced in production Rust. Implement **authenticated full-graph** validation before any future READY/commit, including exact owner/target ancestry, cycles, duplicate slot IDs, revocations and effective recovery routes. A group UUID being nonnil does not establish trusted group membership. |
| **Nonce uniqueness** | W1 shows two separately encoded frames may use the same 24-byte nonce. This is **not automatically a vulnerability** if they use different independently derived AEAD keys. Enforce **nonce uniqueness per actual encryption key** and appropriate CSPRNG generation/nonce-reuse protection. Do not blindly equate nonce reuse across distinct independent keys with PRF-salt reuse, which is an **input factor isolation** problem. |
| **Recovery-code entropy** | Code-only recovery is appropriate only for securely generated **uniform 256-bit** recovery material. HKDF is not a replacement for password stretching. Reject user-chosen/low-entropy “codes” in the trusted generation/provisioning ceremony rather than pretending the slot codec can infer entropy from 32 bytes. |
| **Rollback and historical snapshots** | Exact vault/slot/target context changes prevent simple cross-target context reuse but do **not** invalidate a previously valid slot for the same root. Require authenticated generation/ancestry, explicit S4 limitations, R8 purge-on-rotate behavior and warning about uncontrolled historical backups; don't promise malicious rollback resistance without an independent anchor. |
| **Bounds and transcript alignment** | V3RV test cap 2,048 bytes vs legacy `MAX_SLOT_BYTES=1,024` is a version/representation issue, not evidence of an accepted oversize production slot. V3RV proposed role-tagged IKM differs from frozen V02-B fixed-width IKM; new seal/open and **new** KATs are mandatory and V02-C KATs cannot certify V3RV. |
| **Reported performance and probe claims** | The reviewer's Argon2 measurements are device-specific and the 256-slot number is a hypothetical batch, not the app's proven behavior. P6 and W1 are targeted demonstrations, **not** security proofs or hardware device tests. |
