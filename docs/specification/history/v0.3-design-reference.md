## Executive summary

Vaulty is a local-first password and passkey manager with a Rust cryptographic engine, CLI, daemon, browser extension, native-messaging bridge, password generator, and cross-platform hotkey activation. The application separates global vault state, individual entry secrecy, authenticator trust and relay/client trust.

**Key separation, confirmed for v0.3:** The **Vault Master Key (VMK) protects only the encrypted global control body**: entry index, authenticated policy and trust registries, recovery assignments and other vault metadata. **The VMK is never an input to entry-key derivation or unwrapping.** Every entry is encrypted by its own independent random **Data Encryption Key (DEK)**, itself wrapped under the entry's selected factors. Default entries use a separately generated, independently wrapped **Vault Entry Root Secret (VERS)**. The prior term **DERK** is retired to avoid implying VMK-dependence.

**State and memory, confirmed:** `CLOSED → OPEN → LOADED`, with `LOCKED` clearing loaded metadata. `OPEN` reads only a bounded public header. `OPEN → LOADED` temporarily unwraps the VMK to authenticate and decrypt the control body, then discards the VMK. `LOADED` may keep explicitly classified entry metadata in memory but keeps **no VMK, VERS, entry KEKs/DEKs, activated virtual-authenticator material or entry plaintext**. `READ_OPERATION` uses **only entry authorization factors**, never the VMK. `WRITE_OPERATION` freshly authorizes the VMK for every persistent change, plus entry factors where the secret or its policy is affected; it commits atomically and clears all keys.

**Authentication:** Supported normal vault modes are master password with a password-protected **virtual FIDO2-compatible PRF provider** (single-factor assurance), or master password with a **trusted physical FIDO2** authenticator (hardware-backed). Both use the same high-level provider and wrapping-slot interface, but do not provide the same assurance. The presence of *any* weaker active normal unlock slot determines the effective weakest normal-access path; recovery bypasses are displayed separately.

**Recovery:** One high-entropy vault recovery code is the recommended default. Vault recovery requires `code + master password` or `code + authorized physical FIDO2`; independent authorized slots must be provisioned in advance. Entries have explicit `SHARED`, optional `GROUP` / `INDEPENDENT`, or `STRICT_NONE` recovery policy. Recovery of the VMK never automatically recovers independently protected entries; only preprovisioned VERS/entry-DEK recovery slots permit that.

**Communication:** Trusted FIDO2 authenticators and paired browser/relay clients are separate registries. The browser extension and daemon communicate over an **end-to-end authenticated encrypted channel**, through a transport-only native host unable to inspect credential plaintext. Pairing uses an explicitly trusted local approval path, verified identities, and a fingerprint comparison. An authorized session is not general permission to request secrets; every operation checks client scope, site/target origin, entry policy and authentication freshness.

**Security review disposition:** Accept local-compromise mitigations with explicit limitations, end-to-end relay encryption, weakest-slot warnings, authenticated entry generations and tombstones, explicit user-gesture autofill, trusted pairing approval, key/slot commitment review, metadata-leakage controls, zero-retained root-key rules, safe recovery-code presentation, migration risk controls, fuzzing/supply-chain gates, X11 restrictions, encrypted-swap guidance and denial-of-service-safe throttling. **Retain the intentionally selected virtual provider**, implemented minimally, rather than replacing it with a different password-only pipeline.

**Functional scope:** All **67 original checklist occurrences** remain mapped to **34 consolidated functional requirements** (Section 1; Appendix 21), including CLI/service management, CRUD, generation, passkeys, hotkeys, socket/relay, and recovery. Design coverage is not implementation progress.

## 1. Product scope and functional baseline

### 1.1 Included capabilities

- Create, open, load, browse, lock, close, update, back up and recover local vaults.
- CLI, daemon start/stop/status, password confirmations and bounded interactive attempts.
- CRUD and redacted previews for independently encrypted passwords, passkeys and related entry types.
- Password generation with configurable length and character policy, using operating-system CSPRNG.
- Trusted physical FIDO2 registration, verification, scoping, backup and revocation.
- Password-only unlock through a minimally implemented software/virtual FIDO2-compatible PRF provider.
- Vault and per-entry recovery with explicit precreated slots and loss behavior.
- Authenticated end-to-end browser extension ↔ daemon IPC with native-messaging transport.
- Website credential save/fill with explicit interaction and origin/frame authorization.
- Cross-platform hotkey activation; direct credential typing only where explicitly supported and risk-gated.
- Software passkeys and hardware passkey invocation as a later separately gated milestone.
- Versioned storage, authenticated control index, tested atomic persistence, migration and security verification.

### 1.2 Outside initial acceptance scope

Cloud sync, shared team vaults, hosted recovery, ordinary relay access over the internet, physical-token private-key extraction, platform-independent secure credential typing, automatic passkey provider readiness, and a guarantee of safety against privileged or fully compromised host malware are out of scope. A **hardware-only** unlock mode remains deferred.

### 1.3 Normative language and document status

**MUST / MUST NOT** are proposed acceptance conditions; **SHOULD** is recommended unless a documented review approves a deviation; **MAY** is optional. Status labels describe decisions in this design, not code implementation. The cryptographic combiners, commitment method and protocol handshakes require a reviewed specification and independent test vectors prior to production deployment.

### 1.5 Functional-contract boundaries

- **Entry update vs credential update:** changing a saved website password is distinct from changing a separate password that protects the entry. Both are supported; neither silently changes the other.
- **Partial view vs reveal:** `show partial entry` and `list entries` return only masked, policy-approved metadata. Explicit reveal or credential fill is an exceptional, independently authorized secret-use operation. Public locked-state metadata must not expose site titles or usernames.
- **Device terminology:** `list/add/remove device` in the old checklist is ambiguous; the modern API exposes **authenticators** (FIDO2, physical/virtual) and **clients** (browser/relay installations) separately.
- **Interactive retries:** `verify_pw, three tries` is retained as a configurable interactive UX policy (initial default three), not a claim of offline vault-file brute-force resistance. Physical FIDO2 PIN retry behavior is controlled by the authenticator.
- **Recovery via virtual FIDO2:** the old phrase `Recovery Code for Fido2 into Virtual Device HMAC2` is **reworked**, not silently implemented. Recovery should unwrap an independently provisioned slot with the required two inputs; software must not forge the identity or assurance of a missing physical YubiKey. The virtual provider remains the normal password-only adapter.
- **Hotkeys:** Global shortcut activation remains a feature; direct credential typing is optional and platform risk gated (X11 disabled by default, Wayland deferred, Windows conditional). Neither bypasses entry authorization.
- **Passkey scope:** `generate passkey`, `perform passkey` and incoming passkey registration are distinct from FIDO2 keys used to unlock Vaulty; the WebAuthn provider is deferred until base vault/relay security passes.

## 2. Threat model and security-review disposition

### 2.1 Protected assets and adversaries

Assets: VMK and its envelopes; VERS and virtual-provider material; entry DEKs/KEKs and passkey private keys; recovery codes; plaintext credentials; authenticated global control/index; trusted-authenticator and trusted-client policy; session and origin bindings.

The model addresses offline theft of vault files and snapshots, tampered records, unpaired IPC clients, hostile web pages, compromised native host, stolen/revoked authenticators and same-user malware. A hostile same-user process or browser extension can interfere with UI and input, steal its own identity secrets or observe legitimately released values. Hardening reduces exposure but **does not promise an impenetrable same-user security boundary**. A malicious kernel or privileged debugger is outside the guarantee.

### 2.2 Security review checklist — disposition

| Finding | v0.3 disposition | Requirement / residual risk |
|:--|:--|:--|
| Same-user malware; `SO_PEERCRED` insufficiency | **Accept with refinement** | Linux hardening + separate approval; per-fill explicit gesture; consider separate service identity; no impossible malware immunity claim |
| Native host in credential path | **Accept** | Authenticated E2E extension–daemon encryption; host forwards opaque frames only |
| Weakest slot downgrade | **Accept** | Compute effective weakest normal unlock; separate disclosure of recovery bypass |
| Entry replacement/deletion and whole-file rollback | **Accept** | Authenticated generations, ciphertext hashes and tombstones; optional independently protected rollback anchor |
| Autofill origin/frame/clickjacking attacks | **Accept** | User gesture, exact origin default, frame restrictions, extension-controlled UI and request-binding |
| Pairing approval channel | **Accept with refinement** | Local owner approval + fresh auth + visible fingerprint; cannot guarantee trusted display on compromised OS |
| Noncommitting AEAD / several candidate keys | **Accept as crypto-review item** | Slot/target binding; specify and test reviewed key validation/commitment; do not claim full commitment from an unchecked key-check value |
| Header/size metadata leakage | **Accept** | Minimize public descriptors and use optional ciphertext padding buckets; quantify leakage |
| DERK idle residency | **Superseded / strengthened** | VERS independently wrapped; **no** VMK/VERS/DEK retained while idle in LOADED |
| Recovery-code entropy and display | **Accept** | High-entropy code, checksum/typo detection, confirm backup, no logs/scrollback by default |
| Virtual FIDO2 complexity | **Keep chosen design with constraint** | Minimal PRF-compatible software adapter, no fake 2FA or full CTAP emulation by default |
| Prototype nonce/log exposure | **Accept with qualification** | Inventory risky data and logs; do not silently migrate; rotate potentially exposed secrets according to evidence |
| Missing parser fuzzing/supply chain checks | **Accept** | Fuzz formats/IPC; cargo-audit/deny; SBOM and signed release evidence |
| X11 keystroke snooping / focus race | **Accept** | Shortcut activation supported; typing on X11 disabled by default and never called secure |
| Swap/hibernation leakage | **Accept** | mlock is best effort; encrypted swap, dump/hibernate guidance; residual risk disclosed |
| Interactive throttling lockout abuse | **Accept** | UX throttling only; per-client nuisance limits; avoid easy global lockout; Argon2id protects offline attacks |

## 3. Vault state machine and in-memory visibility

### 3.1 Persistent states

| State | Meaning | Allowed resident information |
|:--|:--|:--|
| `CLOSED` | Vault not open or process not running | No vault-specific state |
| `OPEN` | Vault file opened; public header parsed, not authenticated for use | Public header, encrypted envelopes, opaque framing; no decrypted control body |
| `LOADED` | Owner authenticated; encrypted control body authenticated/decrypted; VMK discarded | Authenticated entry names, usernames, URLs, policy descriptions, trusted registries and encrypted record references; no reusable decryption keys or entry plaintext |
| `LOCKED` | Explicit/automatic lock; metadata and authorizations cleared | Public header only; transport connections may persist with no entry permissions |

The distinction `OPEN` vs `LOCKED` is intentional UI/lifecycle history; their secret visibility is equivalent. On `CLOSED`, close descriptors and wipe all vault-specific process state.

### 3.2 Temporary operation stages

`IDLE → AUTHORIZING → EXECUTING → [COMMITTING for writes] → CLEANUP → IDLE`. Failures or cancellation run `CLEANUP`. Temporary `READ_OPERATION` and `WRITE_OPERATION` are substates **of** `LOADED`, not persistent unlocked states. Concurrency MUST serialize or otherwise safely isolate key-bearing operations and bind each to one authenticated control-index generation.

```text
CLOSED --open vault--> OPEN
OPEN / LOCKED --fresh vault authorization, transient VMK,
                 authenticated control-body read, discard VMK--> LOADED
LOADED --authorized entry read (no VMK)--> READ_OPERATION --> CLEANUP --> LOADED
LOADED --fresh VMK authorization + entry auth if relevant-->
                                    WRITE_OPERATION --> ATOMIC_COMMIT --> CLEANUP --> LOADED
LOADED / READ_OPERATION / WRITE_OPERATION --lock/cancel--> CLEANUP --> LOCKED
ANY --close--> CLOSED
```

### 3.3 Visibility matrix

| Material | OPEN / LOCKED | LOADED idle | READ_OPERATION | WRITE_OPERATION |
|:--|:--:|:--:|:--:|:--:|
| Public header/encrypted slot descriptors | Yes | Yes | Yes | Yes |
| Decrypted control/index metadata | No | **Yes** | Yes | Yes |
| VMK | No | **No** | **No** | Temporary, required for global changes |
| VERS | No | **No** | Temporary **only if entry policy uses it** | Temporary if needed for entry setup |
| Entry KEK and DEK | No | **No** | Temporary for selected entry | Temporary for affected entries only |
| Master/entry password, physical PRF, virtual secret | No | **No** | Temporary required inputs only | Temporary required inputs only |
| Plaintext credential/private software passkey | No | **No** | Temporary only for bounded operation | Temporary only if secret content is modified |

**Metadata is sensitive.** `LOADED` intentionally trades metadata exposure for usability; the UI MUST clearly indicate that entry names, usernames and sites are readable while LOADED, and lock/timeout MUST erase app-managed snapshots and UI models. Do not store password fragments, recovery material or secret-bearing freeform notes in listing metadata.

### 3.4 Read permission while VMK is absent

The authenticated `LOADED` control snapshot contains current entry policy, credential IDs, authorized scopes and the hash/generation of each entry ciphertext. The daemon MUST verify the requested encrypted record matches that snapshot before evaluating policy. The authentication factors unwrap the **entry DEK directly**, possibly through an independently wrapped VERS. VMK is not reacquired. A stale/changed record, revoked device, mismatched generation or locked snapshot causes denial (or a full fresh LOADED transition) rather than an unauthenticated fallback.

## 4. Components and trust boundaries

```text
Untrusted website / iframe
   | limited DOM observations, never an authority to request arbitrary secrets
Paired browser extension (instance identity; user gesture; tab/frame binding)
   |  E2E authenticated encrypted frames (handshake + pinned identities)
Native messaging host (opaque byte forwarder only; replaceable, untrusted)
   |  restricted OS pipe / Unix socket (SO_PEERCRED is defense in depth)
Vaulty daemon (authoritative request/entry/authenticator policy + crypto)
   +-- public header / slot parser
   +-- encrypted global control/index (VMK needed to load/update)
   +-- independently encrypted entry records (VMK not needed for reads)
   +-- physical FIDO2 adapter; minimal virtual PRF provider
   +-- trusted local approval UI and CLI
   +-- atomic storage, backup/migration, redacted auditing
```

**Distinct trust concepts:** (1) an authenticator proves possession of an enrolled FIDO2 credential; (2) a relay proves possession of its paired client identity; (3) a live request is separately authorized for a specific operation and destination. Neither possession alone permits arbitrary secret export.

### 4.1 Public bootstrap versus encrypted authority

The locked-state public header provides enough opaque descriptors to select candidate VMK/VERS/recovery envelopes, but **not** the confidential key material. Encrypted authoritative registries load only during `OPEN → LOADED`. A minimal local client-identity cache can authenticate transport connections while locked, but cannot grant entry operations; it is validated against the encrypted client registry after LOADED. If the registry and cache disagree, deny and require local repair/re-pairing.

**Critical constraint:** If an entry read must work without a VMK, the encrypted VERS envelope and that entry's independently encrypted DEK envelopes **must remain accessible as ciphertext without decrypting the global control body**. They can be stored as opaque envelope records referenced by the authenticated control index. This is the formal solution to the VMK/entry dependency problem in v0.2.

## 5. Versioned file format and integrity

### 5.1 Logical file layout (proposed next format)

```text
PUBLIC_HEADER                     [plaintext framing, no secrets]
  magic, version, vault_id, bounded suites/KDF parameters,
  opaque slot references + encrypted VMK / VERS bootstrap envelopes,
  control-record locator, entry-record/manifest framing hints

ENCRYPTED_CONTROL                 [AEAD under VMK-domain subkey]
  metadata index (titles/usernames/sites; no entry secrets),
  entry IDs, current generation + ciphertext hash, tombstones,
  policy/slot scope descriptors, TrustedAuthenticators, TrustedClients,
  recovery-group assignments, security-assurance state and audit pointers

OPAQUE_INDEPENDENT_KEY_ENVELOPES  [accessible as ciphertext without VMK]
  VERS wrapping slots; entry DEK wrapping slots; recovery/group slots;
  per-slot purpose, version, factor descriptor, unique nonce and binding

ENCRYPTED_ENTRY_RECORDS           [AEAD under independent per-entry DEK]
  opaque ID, immutable crypto context, nonce, ciphertext,
  encrypted password/passkey/note contents; no direct plaintext
```

The public header must not include entry titles, usernames, URLs, plaintext virtual-provider secrets or the VERS. The format must permit a loaded daemon to locate encrypted entry envelopes and ciphertext without reopening the VMK-protected control body. Public parsing is **untrusted** until authenticated via the VMK-backed control body and suitable envelope validation.

### 5.2 AAD, key identity and key commitment

AAD for entry payloads binds immutable vault ID, entry ID, record purpose, algorithm and format version. Envelope AAD binds target-key ID, slot ID, factor policy, credential scope, nonce/algorithm ID and relevant generation. Changing slots or policy does not force rewriting unchanged entry ciphertext; authenticated control state separately binds current policy, envelope set, ciphertext hash and generation.

**OPEN-CRYPTO-01:** XChaCha20-Poly1305 is not a generally key-committing AEAD. Because Vaulty can have multiple candidate slots, implementation MUST choose and review a specific key-validation/key-commitment strategy before a release. A simple published key-check value is not automatically equivalent to a committing construction; the design must avoid accidental offline guessing shortcuts or cross-key confusion. The exact combiner, AAD/commitment transcript and test vectors remain **not yet specified**.

### 5.3 Entry changes, deletion and rollback

The authenticated control index MUST commit to `(entry_id, current_generation, ciphertext_hash, slot_set_hash, protection_policy_version)`. Deleted entries get authenticated tombstones or an equivalent append-only/manifest deletion record. Before a `READ_OPERATION`, the daemon verifies the record and slot set against the loaded snapshot. A forged, dropped or stale individual entry is rejected.

**Whole-file rollback:** an attacker restoring a complete old, correctly authenticated vault may also restore revoked slots and clients. Local OS keyrings are not necessarily monotonic or protected from same-user malware. A TPM-backed monotonic anchor or independently protected state may offer stronger detection, but portability and backup recovery implications are **OPEN**. Without such an anchor, Vaulty MUST explicitly disclose that old authenticated backups can still authorize old credentials.

### 5.4 Atomic updates and nonce discipline

Every changed encrypted record and envelope MUST use a fresh nonce under its key. Atomic saves use owner-restricted temporary files, file `fsync`, rename/replace and parent-directory `fsync` where supported, plus a coherent manifest generation. For entry metadata-only changes, **entry ciphertext bytes remain unchanged**; the control record is re-encrypted. Crash/replay tests and restore tests must cover partial commits. A whole-file encrypted-body design that forces VMK usage on each entry read is **not** the target architecture.

## 6. Keys, independence and operation-scoped access

| Symbol | Key/secret | Source | Purpose and lifetime |
|:--|:--|:--|:--|
| `VMK` | Vault Master Key | CSPRNG, 256 bits | Global control/index AEAD root only; loaded and cleared per global operation |
| `VERS` | Vault Entry Root Secret (replaces `DERK`) | CSPRNG, 256 bits | First input for default entry KEKs; independently wrapped, never derivable from VMK |
| `DEK_e` | Entry Data Encryption Key | CSPRNG, 256 bits per entry | Encrypt one entry payload; never held outside that operation |
| `KEK_slot` | Wrapping key | Reviewed password/PRF/KDF combiner | Wrap VMK, VERS or DEK for **one** slot, purpose and context |
| `P_master`, `P_entry` | Master/entry password secret | User input → Argon2id | Authentication inputs; wipe promptly; no caching |
| `PRF_fido` | Hardware FIDO2 credential PRF | Verified trusted physical device | May satisfy physical policy; ephemeral and scope-bound |
| `PRF_virtual` | Software credential PRF | Password-bootstrapped virtual provider | Keeps interface uniform; **not** an independent factor |
| `R_code` | Human-recoverable high-entropy code | OS CSPRNG, e.g. 256-bit | Recovery KEK input; never persist in plaintext |

**Non-derivation invariant:** `VMK ↛ VERS ↛ entry-DEK generation`. VERS is independent of VMK and entry DEKs are independently random. VMK cannot unwrap an entry DEK. VERS is an **input** for authorized default-entry KEKs, not the entry's own DEK; losing VERS does not change stored entry ciphertext but may make its wrapping slot unusable absent recovery.

### 6.1 Normal entry KEK architecture

An entry has one random `DEK_e`. For each authorized normal or recovery path, a versioned envelope encrypts **that same DEK_e** under a slot-specific KEK derived from the required inputs. The exact combined-factor KDF MUST be documented and independently reviewed; do not implement arbitrary concatenation or XOR as if it were verified cryptography.

```text
Entry e: random DEK_e ---> XChaCha20-Poly1305(entry payload)
                            (ciphertext stays unchanged on slot rewrap)

First input:  custom entry password --Argon2id--+
          OR independently wrapped VERS --------+
                                                   -> reviewed, domain-separated KEK
Second input: virtual FIDO2 PRF (software) ----+    -> unwrap DEK_e
          OR  trusted physical FIDO2 PRF ------+

Change input / add trusted key: authenticate existing DEK_e,
create new envelope(s), atomically commit index + slots, discard DEK_e.
```

**Default entry VERS bootstrap:** The VERS is not inside VMK-encrypted data as its sole reachable envelope. It has independently authorized wrappers that can be unlocked during an entry request, e.g. through a password+virtual or password+physical path, or explicitly provisioned recovery. In the default policy, accessing VERS is an **entry secret authorization step**, not a metadata or VMK step. It may require the master password, but not the VMK. If the entry additionally requires a physical FIDO2 PRF, the same authenticator can be invoked with domain-separated requests under the same bounded operation as permitted by device semantics; **no PRF output is reused across unrelated purposes**.

**Custom-password entry:** Its DEK can be unlocked using the custom password and the configured virtual/physical authenticator without VMK or VERS. The virtual provider's encrypted secret must be bootstrappable from the appropriate user-entered knowledge input without needing VMK or VERS that it is intended to unlock. Where a virtual provider is tied to a master password instead, the UI MUST disclose the extra required input. No circular bootstrap is permitted.

### 6.2 Entry policies

| Policy ID | First input | Second input | VMK on read? | Meaning |
|:--|:--|:--|:--:|:--|
| `ENTRY_DEFAULT_VIRTUAL` | On-demand VERS | Virtual FIDO2-compatible PRF | **No** | Convenient default; single-factor/knowledge-root assurance |
| `ENTRY_PASSWORD_VIRTUAL` | Separate entry password | Virtual PRF bootstrapped by authorized password input | **No** | Entry password protection; virtual is not 2FA |
| `ENTRY_DEFAULT_PHYSICAL` | On-demand VERS | Explicitly authorized physical FIDO2 PRF | **No** | Entry requires active trusted hardware |
| `ENTRY_PASSWORD_PHYSICAL` | Separate entry password | Explicitly authorized physical FIDO2 PRF | **No** | Strongest normal entry isolation |

The **first input** for `ENTRY_DEFAULT_*` is a stable VERS that must itself be independently unwrapped when needed. A default entry's effective assurance is limited by **every active path to VERS and the entry DEK**, including recovery slots. Multiple authorized physical authenticators require distinct PRF/DEK envelopes. A virtual provider MUST NOT satisfy a physical-required entry slot.

### 6.3 Rewrap versus data-key rotation

| Event | Required work |
|:--|:--|
| Change master password | Rewrap affected VMK and VERS/bootstrap/recovery envelopes that depend on it; no entry payload re-encryption by default |
| Add/remove trusted FIDO2 | Add/remove only permitted VMK, VERS and entry-DEK slots; enforce scope and availability checks |
| Change custom entry password | Rewrap affected entry DEK; payload bytes unchanged |
| Change entry recovery path | Authenticated old entry access plus creation/removal of authorized recovery slots |
| Change entry contents | Encrypt new payload under suitable DEK with a fresh nonce; update ciphertext hash/generation |
| Rotate VMK after compromise | Rotate global metadata encryption root and affected envelopes; entry payloads **not** automatically decrypted or re-encrypted unless independently impacted |
| Rotate VERS | Rewrap VERS-dependent entry slots; requires authorized access to affected DEKs; may be infeasible for inaccessible strict entries |
| Rotate entry DEK after compromise | Re-encrypt that entry payload and replace all its normal/recovery envelopes |

Removing a key slot cannot render historical snapshots unreadable. Compromise response must consider old vault copies and old plaintext exposures.

## 7. Vault authentication and authenticator providers

### 7.1 Normal and recovery modes

| Mode | Required user inputs | Provider/slot | Security statement |
|:--|:--|:--|:--|
| `PASSWORD_VIRTUAL` | Master password | Password-unlocked virtual PRF provider, VMK slot | **Single factor**; software-only |
| `PASSWORD_PHYSICAL` | Master password + trusted physical FIDO2 | Verified physical PRF + VMK slot | Hardware-backed multiple factors |
| `RECOVERY_PASSWORD` | Recovery code + master password | Independent recovery VMK slot | Emergency path; code must remain separate |
| `RECOVERY_PHYSICAL` | Recovery code + preauthorized physical FIDO2 | Independent recovery VMK slot | Emergency path; requires available authorized hardware |
| `HARDWARE_ONLY` | Physical FIDO2 + UV | Future distinct VMK slot | **Deferred**, not assumed supported |

If password-only and physical slots both remain active, the **normal vault assurance is password-only** regardless of which method the user most recently selected. Vaulty MUST display all active normal unlock paths and the lowest effective assurance, while listing recovery bypass paths separately. Adding a weaker slot requires explicit administrative consent. No automatic downgrade on missing hardware.

### 7.2 Virtual provider bootstrap and scope

The software provider exists **because the chosen product design requires a common PRF interface**. Implement only registration/identity, bounded challenge/purpose and keyed PRF operations needed for Vaulty—not a pretend USB key or generic WebAuthn authenticator unless separately specified. Store its secret material as an encrypted bootstrap envelope using a user-entered password-derived key (or appropriate entry credential), **never under VMK as the sole protection**. Activate only during the operation; zeroize secret/PRF material before returning to LOADED.

This offers consistent implementation but **does not add an independent security factor**. Validate that a password change can renew its bootstrap/wrapping relationships safely and without silently changing entry payload ciphertext.

### 7.3 Physical provider requirements

Enrolled FIDO2 credentials must pass registration and assertion verification, credential/RP/challenge binding, PIN/UV requirements, and explicit PRF/hmac-secret capability negotiation. Do not derive a KEK from an unverified assertion. Physical class is not proved merely by a credential ID or marketing label; support honest assurance labels for non-attested devices and require attestation when a policy explicitly promises attested hardware.

## 8. Individual entry lifecycle and memory requirements

### 8.1 `READ_OPERATION` without VMK

1. Require state `LOADED` with current authenticated control index; authenticate client and validate requested action/destination.
2. Bind entry ciphertext hash, generation, policy version and slot set to the loaded authenticated snapshot.
3. Request required entry factors (custom entry password or independently unwrapped VERS, and software or hardware PRF); verify device scope and freshness.
4. Derive slot KEK, unwrap selected `DEK_e`, decrypt **only** the requested entry, and execute a bounded operation (`fill`, `reveal`, `sign`, etc.).
5. Return only action-specific minimal output/receipt (for a browser fill, encrypted directly to its paired extension session); never return VMK, VERS, DEK or passkey private key.
6. Release plaintext and every key/input during `CLEANUP`; return to LOADED without any reusable secret.

An entry record is never eagerly decrypted just because the vault reaches LOADED. In the browser, a filled value is necessarily exposed to the destination page; such exposure is an intentional operation, not a claim of end-to-end secrecy from the site.

### 8.2 `WRITE_OPERATION` with fresh VMK

1. Require an explicit edit or administrative request while LOADED; reauthenticate under the selected **authorized VMK slot** for **every persistent file change**.
2. If the requested change affects an existing entry's secret, policy, DEK envelope or recovery, require independent entry factors or a preprovisioned entry recovery path. **VMK possession alone is insufficient.**
3. For a new entry, create a random `DEK_e`, choose entry policy, acquire the necessary VERS/custom password and authenticator input, and seal the new payload/envelope.
4. Load/validate the current committed index generation; update relevant encrypted metadata, generations, tombstones and hashes; write changed records with unique nonces.
5. Persist atomically, verify commit and update LOADED metadata snapshot. On conflict, stale generation or failure, abort or retry only after safe reauthorization as needed.
6. Clear VMK, VERS and any entry-specific secrets **even if** the write fails or is cancelled. Do not keep an uncommitted decrypted state in a background cache.

This model intentionally prompts reauthentication for entry addition, update, deletion, authenticator/client enrollment, recovery-policy change and any other persistent mutation. The process can remain running and paired browser sessions can remain connected without carrying any vault key.

### 8.3 Memory and local-process hardening

Passwords, VMK, VERS, DEKs, virtual-provider secrets, PRF outputs and entry plaintext exist temporarily during their specific cryptographic operation; it is impossible to execute cryptography with zero transient key memory. Implement scoped ownership, secret-aware types, best-effort explicit zeroization (including on error/cancellation/panic boundaries), minimum copies, nonlogging and no caches. Consider `mlock`, `MADV_DONTDUMP`, `PR_SET_DUMPABLE=0`, `RLIMIT_CORE=0`, ptrace/Yama policy and systemd sandboxing, all with documented platform constraints. Prefer encrypted swap and appropriate hibernation policy; these controls do not protect against a fully compromised host or browser.

**LOADED metadata is an intentional exception:** titles, usernames, URLs and policy labels may persist in process/UI memory. Lock must clear daemon and UI metadata models, cancel pending secret operations, invalidate operation-scoped authorizations, and notify extensions. There is no persistent “unlocked with VMK” state and no standard-versus-hardened session choice in v0.3.

## 9. Vault, VERS and entry recovery

### 9.1 Recovery-code model

Generate one high-entropy user-held **vault recovery code** by default (recommended 256 random bits, human-readable encoding and typo-detection checksum). Code creation/confirmation MUST avoid logging and normal terminal scrollback by default; warn against unencrypted screenshots, cloud notes and co-storage with the vault. The code itself is never retained as plaintext.

The two confirmed vault recovery combinations are:

- `recovery code + master password`, or
- `recovery code + authorized registered physical FIDO2 credential`.

Each is a separately preprovisioned **VMK recovery envelope**, not an imitation of a missing YubiKey. No code-only vault recovery is implicitly enabled. If a password-only user loses the master password and has no registered recovery-capable physical authenticator, **the two approved combinations provide no usable recovery path**, even if the code survives. Setup MUST show this explicitly; a third alternative requires a new owner decision, not silent weakening.

### 9.2 Entry recovery, independent from VMK recovery

| Entry recovery policy | Scope | Mechanism |
|:--|:--|:--|
| `SHARED` (recommended ordinary-entry default) | One vault code | **Preprovisioned** DEK or VERS recovery slots using code + master password or code + authorized physical authenticator, according to entry policy |
| `GROUP` / `INDEPENDENT` | Selected high-value entries | Separate group/entry recovery code + required second input, with independently wrapped affected DEKs |
| `STRICT_NONE` | Maximum isolation | **No** recovery envelope; losing all approved factors permanently loses entry access |

A recovered VMK is **not** permission or key material to recover any entry. Entry and VERS recovery must be granted by separately created encrypted envelopes; a globally authorized authenticator is not automatically allowed on every entry. Entry recovery and mode change may alter effective assurance and must be disclosed. A per-entry code for every entry is **not required**; group recovery is optional. Recovery cannot be added after all ways of unwrapping the DEK are lost.

### 9.3 Recovery procedures and limitations

After valid recovery, create replacement slots, revoke current compromised paths and atomically commit the policy/index. Recovery paths do not reveal forgotten passwords. Protect independently encrypted old backups; deleting a slot now does not revoke an old file copy. An entry with strict policy and no available authorized path remains unrecoverable. Backup FIDO2 must be explicitly granted per-entry scope if intended to replace the primary key there.

**Assurance warning:** With an entry normally requiring custom password + physical FIDO2, a recovery slot using code + master password is a deliberate alternative that can bypass those normal factors. It is not hidden or automatically present in strict entries.

## 10. Trusted FIDO2 authenticator management

Maintain an encrypted `TrustedAuthenticators` registry with `id`, label, class (`virtual` / `physical` / attested where verifiable), RP/credential ID, public key, PRF and UV capabilities, permitted vault/VERS/entry/recovery scopes, state (`pending`, `active`, `suspended`, `revoked`), enrollment/revocation generation and audit metadata. The **slot** identifies the exact credential; registry status determines whether it is still authorized. The public header carries only enough opaque information to attempt pre-load authentication.

**Enrollment:** (a) local owner-initiated administrative flow and fresh VMK authorization; (b) register the new FIDO2 credential and verify assertion/PRF/UV/class requirements; (c) show fingerprint, class and requested scopes through trusted UI; (d) for each explicitly authorized target, unwrap its VMK/VERS/entry DEK **using its existing authorization**, create a distinct new envelope, and atomically commit registry and slots; (e) test new permitted path before activation. A newly presented unknown device may be **enrolled** after proof and approval, but it is never treated as trusted merely because it is plugged in.

**Revocation:** require strong owner authorization, check loss of last valid vault/entry/recovery path, invalidate existing operations, retire current slots and update the authenticated index. If the key may be compromised, offer DEK/VMK/possibly VERS rotation with explicit historical-backup caveat. The daemon must never silently use an unauthorized replacement authenticator or a virtual factor for a hardware slot.

## 11. Trusted clients, E2E IPC and approval

### 11.1 Two registries and least privilege

`TrustedClients` contains per-installation or browser-profile identity key/fingerprint, client class, capabilities (`lock_state`, `list_metadata`, `generate`, `fill`, `save`, etc.), permitted origin constraints, status, expiration and revocation generation. A browser extension's published extension ID is an additional browser manifest allowlist—not a unique private client credential. No permission for a paired client to add authenticators, recovery slots or other clients by default.

### 11.2 End-to-end encrypted extension–daemon transport

The browser extension and daemon must mutually authenticate an encrypted application session and pin the established peer identities. The native host transports **opaque ciphertext frames**; it is not a secret-bearing trusted endpoint. An attacker swapping a user-writable host may block or replay delivery but MUST NOT decrypt or silently modify accepted secret-bearing frames. Bind session nonce, transcript, client identity, request ID, action, version, expiry and response to prevent replay/cross-request confusion.

**Protocol direction:** evaluate Noise_XX for initial pairing with explicit fingerprint comparison and an authenticated identity/pinned-key mode for subsequent connections. The particular Noise pattern, selected Rust/extension implementations, channel rekey schedule and replay model require a focused, independently reviewed protocol document; **the presence of Noise_XX alone does not authenticate a first-contact identity**. Threat-model compromise of the extension runtime and its client private key separately: E2E encryption protects against host replacement, not against malicious code already executing in the trusted extension itself.

### 11.3 Pairing, approval and locked state

Unpaired clients may request pairing or nonsensitive status only. A separate local Vaulty approval UI displays the claimed client, cryptographic fingerprint, requested permissions and a user-verifiable comparison; approval requires fresh owner administrative authentication. The same newly paired client cannot approve itself through the socket. Pairing results in a signed/authenticated registry update and encrypted client-state commit requiring VMK authorization. On a compromised desktop, UI spoofing remains a residual risk; optional hardware-backed owner confirmation can strengthen high-assurance enrollment.

While `OPEN`/`LOCKED`, a minimal identity cache and restricted IPC/peer credentials can prove a registered transport identity, but **not authorize entry operations**. In `LOADED`, the daemon consults the authenticated authoritative registry; cache disagreement denies access and triggers local repair. Linux `SO_PEERCRED` and `0600` socket permissions are defenses, not same-user isolation.

### 11.4 Request authorization

Every request MUST independently enforce: pairing state → client permission → explicit user gesture where required → genuine tab/frame/site-origin binding → requested entry and action → appropriate entry factors/freshness → minimal response. A read-only metadata permission never implies credential access; filling one entry never implies listing/exporting every secret. Administrative changes always require a trusted local flow, fresh VMK authorization and any required entry-level factors.

## 12. Browser, passkeys, hotkeys and generator

### 12.1 Browser autofill and credential saving

Do not autofill on page load. Every fill requires a deliberate user gesture; match exact origin by default. Broader domain sets require an explicit reviewed public-suffix/related-origin policy. Deny cross-origin frames by default and bind tab ID, frame ID, document/navigation identity, extension-controlled UI action, selected entry and allowed origin at request and delivery. Revalidate before releasing data; do not treat a page-controlled button or claimed `origin` string as authority. The destination page necessarily receives its form-field content. Save/update requires explicit owner action, an authenticated write operation with fresh VMK, and a durable commit receipt.

### 12.2 Passkey boundary

`EntryType::Passkey` is not equivalent to a complete passkey provider. A software passkey's encrypted private key is unwrapped only in an authorized signing operation, never returned to an extension/native host. WebAuthn RP/origin/challenge/user-verification semantics and counters require separate acceptance. A hardware-backed passkey stays in its physical authenticator; Vaulty never exports or clones its private key. Passkey provider implementation is **deferred** behind vault, entry and browser-security gates.

### 12.3 Password generator and redacted entry preview

Password generation must support length/allowed characters and reasonable presets, validate impossible constraints, use an OS CSPRNG and avoid modulo bias. A generator may run without VMK if it does not persist anything. `list_entries` and `preview_entry` show LOADED metadata only; a secret `reveal` is a distinct entry-authorized operation and must not return long-lived reusable objects.

### 12.4 Hotkey roadmap by platform

| OS/session | Global shortcut activation | Direct secret typing | Priority/assurance |
|:--|:--|:--|:--|
| Windows | Supported with native hotkey API | Optional after explicit authorization and target revalidation | Activation **P2**; typing **P3**, not guaranteed secure |
| Linux X11 | Supported as convenient launcher/selector | **Disabled by default**; unsafe explicit opt-in only if retained | Activation **P2**; typing **P3/unsafe** |
| Linux Wayland | Prefer `xdg-desktop-portal` GlobalShortcuts where supported; fallback launcher | **Deferred** absent a reviewed securely bound destination integration | Activation **P2**; typing **deferred** |

Shortcut activation must not retrieve a credential itself. The hotkey operation calls the same daemon authorization path as CLI/browser operations. Window focus checking suffers a check-then-type race on Windows and X11; do not advertise typing as a secure delivery guarantee. Prefer browser extension filling for websites.

## 13. Storage safety, rollback and prototype migration

Atomic vault writes require narrow file permissions, temp-file `fsync`, atomic replace, parent `fsync` where supported, coherent metadata generation and backup/recovery tests. Multi-file layouts require authenticated manifests and transaction rules rather than assuming per-file atomic writes produce an atomic vault.

**Migration/security gate:** The previously inspected prototype uses a fixed master nonce on repeated sealing and prints decrypted vault-body bytes during unseal. Old vaults **must not** silently parse as the new format. Detect old versions, make a safe backup, assess exposure (old ciphertext copies, console history, logs, system backups), recommend rotation where data plausibly leaked, and test reopen before final cutover. Not every old credential is proved compromised merely because the defect existed; where exposure cannot be ruled out, use conservative rotation guidance.

Key revocation and encrypted-index authenticity do not alone defeat full-file rollback. Any external counter/anchor adds portability, privacy, restore and failure-mode requirements; specify those before advertising rollback prevention. Treat lost backing key/counter as potential availability failure and document recovery.

## 14. Runtime hardening and assurance limits

The Linux daemon should use `PR_SET_DUMPABLE=0`, disable core dumps via `RLIMIT_CORE`, configure appropriate ptrace policy, reduce OS capabilities and consider systemd sandboxing/seccomp, `mlock` and `MADV_DONTDUMP` where feasible. Use encrypted swap and document hibernation limits. An unprivileged same-user process can still manipulate input/extension UI in many environments, and a stolen client private key might permit impersonation. Isolating the daemon under a separate service identity may improve matters but creates a deployment/IPC design decision.

Interactive three-attempt checks are user-experience controls only. Offline attackers can test file copies; rely on Argon2id cost and strong secrets. Avoid a globally exhaustible retry budget that untrusted local clients could use to lock out the rightful owner. Require bounded, per-client pacing and sensible request limits; never let unauthenticated requests force expensive KDF work without admission control.

## 19. Open decisions and required design reviews

| ID | Question | Current conservative direction |
|:--|:--|:--|
| OPEN-01 | Exact combined-factor PRF/password KDF construction and key commitment | Independently review algorithm/transcripts; test vectors; **do not ship without resolution** |
| OPEN-02 | Virtual provider bootstrap for custom-password entries | Bind to entry password (or disclose master-input dependency); require no circular VERS/VMK bootstrap |
| OPEN-03 | Shared recovery code automatically on all ordinary entries? | Recommend opt-in at vault setup with visible per-entry inherited policy; strict entries always exempt |
| OPEN-04 | Password-only lost master with no physical backup remains unrecoverable | Preserve two recovery combinations unless owner explicitly approves a third path |
| OPEN-05 | Hardware attestation and trusted UI guarantees | Distinguish verified physical presence from attested hardware; evaluate separate protected service/UI identity |
| OPEN-06 | External rollback anchor and portable backups | Design with recovery/restore tradeoffs, never assert rollback resistance from file authentication alone |
| OPEN-07 | Padded record buckets and opaque header slots | Evaluate leakage and cost; retain bounded predictable bootstrap |
| OPEN-08 | Noise_XX pairing versus pinned-key established-session pattern | Require authenticated fingerprint, key storage/rekey/replay design and security test plan |
| OPEN-09 | UI metadata privacy while LOADED | Retain browsable metadata with explicit timeout; consider optional metadata-minimal listing later |
| OPEN-10 | Scope of mandatory fresh user presence for fill | Gesture every fill; fresh FIDO2 for physical policies; trusted UI confirmation for high-assurance entries |
| OPEN-11 | Recovery groups in first MVP | Version format now, defer group UX if MVP schedule requires |
| OPEN-12 | Windows/X11/Wayland typing implementation | Only shortcut activation P2; Windows typing P3 conditional; X11 unsafe opt-in; Wayland typing deferred |
| OPEN-13 | Daemon systemd user service or restricted separate service identity | Measure compromise isolation against deployment complexity; preserve CLI lifecycle |
| OPEN-14 | Whether VMK must be present for writing bytes of independent entry records | **No:** only an authorized control/index update requires VMK; the entry bytes themselves remain independently encrypted |
