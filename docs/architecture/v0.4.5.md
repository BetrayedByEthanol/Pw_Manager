# Vaulty v0.4.5 — Architecture

**Status:** Target architecture (not implemented) | **Last reconciled:** 2026-11-06  
**Normative counterpart:** [v0.4.5 specification](../specification/v0.4.5.md) | **Implementation evidence:** [acceptance register](../roadmap/acceptance-register.md)

## System context and boundaries

```text
Untrusted website / DOM / frames
    |
    | content script: selection, constrained fill, page-origin observation
    v
Browser extension [popup/options + service worker]
    | explicit user gesture, requesting installation identity
    | E2E authenticated ciphertext (planned; not implemented)
    v
Native Messaging host [transport only: no vault keys, no plaintext, no policy decisions]
    | bounded local forwarding / Unix domain socket
    v
Vaulty trusted daemon [single authoritative operation-policy engine]
    +-- trusted local approval and PIN/password prompt helper (pinentry-style)
    +-- session state machine / client capability enforcement
    +-- FIDO2 physical authenticator adapter (fresh per physical entry read)
    +-- virtual PRF adapter (software, LOADED only; no extra factor)
    +-- vault serializer/transaction manager
    +-- canonical cryptographic engine and recovery-slot manager
    +-- trusted-authenticator registry + trusted-client registry
    |
    v
One portable vault file + optional non-authoritative local telemetry
```

The CLI talks to the **same daemon-side policy engine**, not a shortcut to filesystem or keys. The hotkey integration may activate a protected UI, but may not bypass an authorized entry-use operation. Software/hardware passkey support is a separately reviewed provider surface.

## Trust-boundary table

| Boundary | Caller trust | Mandatory enforcement |
| --- | --- | --- |
| Website → extension | Untrusted page content | No page-controlled credential release; exact origin/frame/user gesture |
| Extension → native host | Extension installation identity | Authenticated E2E session to daemon; identity binding |
| Native host → daemon | Host not inherently trusted | Bounded IPC, client/installation identity, replay and capability checks |
| CLI/UI → daemon | OS user identity insufficient by itself | Local trusted approval + per-operation authentication |
| Daemon → FIDO2 device | Authenticator identity/UV must be verified | Registered active credential, correct scope/RP, fresh PRF/assertion |
| Daemon → filesystem | Vault bytes may be malicious or rolled back | Bounded parser, authenticated states, crash consistency, ancestry warning |
| Daemon memory | Same-user/OS compromise possible | Minimal lifetimes, masked VERS, controlled release, best-effort cleanup |

A socket at mode 0600 or SO_PEERCRED alone does not prove the requested operation is authorized. Hardware and virtual providers are not interchangeable. Do not conflate the physical FIDO2 device registry with the trusted-client registry.

## Single-file layout (conceptual, not byte-level freeze)

```text
Vault file
 ├─ bounded/versioned public header
 │    ├─ format identifier, envelope framing, KDF parameters, opaque slot hints
 │    └─ minimum exposed metadata (no secrets, names, URLs or raw auth registry)
 └─ authenticated VMK-encrypted control body
      ├─ generation, vault ID, policy and trust registries
      ├─ entry index [ID, encrypted-record hash, generation, tombstone]
      ├─ VERS / VMK / entry slot descriptions and recovery coverage
      ├─ independent per-entry AEAD ciphertext records
      │    └─ each record encrypted under its own random DEK
      └─ signed/hashed ancestry context (authenticated within current body)
```

The outer VMK protects the file's control body at rest; individual entry ciphertext has its **own** independently wrapped DEK. During OPEN → LOADED the outer body is authenticated/decrypted, then VMK is discarded. LOADED retains only allowed authenticated metadata and still-encrypted entry records. Entries can thus be accessed later without VMK; a READ_OPERATION derives its entry KEK from entry factors.

The **canonical wire schema, nonce/AAD bindings, padding, index ordering, commitment and metadata leakage budget are NOT frozen** until cryptographic review (OPEN-01, OPEN-15). Do not implement the old VLT1 byte layout as canonical.

## Key graph

```text
Master-password KDF + physical/virtual vault factor
                    |
           authorized VMK slot ─── VMK ──> outer control body only
                    ^
        recovery-code routes (pre-provisioned)

Independently generated VERS  (LOADED: two-share XOR representation)
       |
       +-- entry default first input + [entry-selected virtual OR fresh physical PRF]
                                       |
                     context-bound, reviewed entry KEK (OPEN-01)
                                       |
                             wrapped independent entry DEK
                                       |
                                entry ciphertext

Custom entry password + [entry-selected virtual OR fresh physical PRF]
                  |
          reviewed entry KEK -> wrapped entry DEK -> entry ciphertext

Recovery: separate pre-authorized slots for VMK / VERS / selected DEKs
```

No VMK-to-VERS or VMK-to-entry-DEK derivation link is allowed. VERS fanout is intentional for ordinary default entries and must appear in blast-radius/assurance reporting. A recovery route is an alternative key-unwrap path, not an invented provider or a fake hardware signature.

## State machine and operation protocol

| State/operation | Contents and permitted action | Key lifetime |
| --- | --- | --- |
| CLOSED | No file/session; no vault secrets | None |
| OPEN | File acquired, bounded public header only | None |
| OPEN → LOADED | Validate slots; fresh VMK authorization; authenticate/decrypt control body | VMK temporary, then wiped |
| LOADED | Authenticated index and encrypted records, masked VERS shares, activated virtual adapter | No plaintext VMK/DEK/KEK/entry secret |
| READ_OPERATION | Authorize entry; derive only scoped KEK; decrypt its DEK + requested payload | Short-lived; wipe after operation |
| WRITE_OPERATION | Fresh VMK authorization; additional entry authorization as required; atomic transaction | Short-lived; wipe after commit/cancel |
| LOCKED | Clear metadata, VERS shares, virtual adapter and all outstanding operations | None |
| Close/reopen | Cancel, clear, release file handles; begin at CLOSED/OPEN | None |

The masked VERS in LOADED is an **approved exception** relative to older v0.3 prose. Two shares are insufficient against an attacker who reads both; rotate representation after use and clear on LOCKED. The virtual provider's storage/lifetime must be bounded by LOADED. Physical policies require a real fresh device operation per entry read regardless of earlier token use.

### Example: authorized browser credential fill

1. An explicit click/gesture in a trusted extension surface authorizes *request intent*, not release by itself.
2. The extension creates an E2E request bound to installation/session, tab/frame, origin, entry and action; the native host forwards opaque bytes.
3. The daemon authenticates the client and checks capabilities, origin, state, policy, revocation and freshness.
4. Default+virtual uses reconstructed masked VERS + virtual provider; default+physical uses VERS + fresh FIDO2 operation; custom entries request their password plus the selected provider. There is **no VMK/master-password prompt** while LOADED for reads.
5. Derive scoped KEK; unwrap the independent DEK; decrypt only requested data; route through E2E response to approved extension sink. Wipe plaintext keys and rotate masked VERS representation.
6. Record optional loss-tolerant usage telemetry without VMK write. The response and receiving UI must avoid inadvertent logs and page disclosure.

### Example: add or change an entry

1. Require owner authorization for the WRITE_OPERATION and fresh VMK unwrap.
2. Enforce entry-level factor policy for affected secrets; for a new entry mint an independent random DEK and fresh AEAD nonce.
3. Bind policy + entry ID + vault ID + generation + slot ID in reviewed authenticated context. Update authorized index and tombstones.
4. Write a new file generation atomically, retain prior verified recovery generation, fsync and reopen/validate.
5. Discard VMK and operational keys. Do not rewrite unrelated entry DEKs absent explicit rotation/compromise requirements.

## Recovery provisioning and key rotation

The normal read path **never** needs a recovery-code prompt. Creating/changing a code-dependent VMK, VERS or DEK recovery slot **does** need the appropriate code at that moment (approved Option A). New physical-device recovery routes require the new device PRF; incomplete enrollment stays PENDING/UNVERIFIED, not active. Isolated entries require hardware on every recovery route or STRICT_NONE; code-only recovery is illegal for an isolated DEK. INDEPENDENT source schema is retained but user-facing setup is deferred. Old slots must remain active until new coverage and reopen are verified.

## Transaction and migration engine

The same low-level transaction machinery serves normal writes, safe legacy upgrade, vault-to-vault transfer and manual distinct-vault merge, but these are **different authorization workflows**.

```text
Preflight source version + authorization + source snapshot
    -> parse & verify source (no silent import)
    -> choose target + resolve IDs/policy conflicts explicitly
    -> mint destination-specific keys/slots/nonces
    -> isolated destination temp + fsync + rename + parent fsync
    -> reopen, cryptographically verify and compare transaction manifest
    -> finalize (or retain source + recovery instructions on failure)
```

N-01 format migration is P0; N-02 selective copy/move P1; N-03 explicit two-vault merge P2. N-04 automatic sync-conflict merge is separate deferred P3 and not covered by the transaction engine alone.

## Deployment and portability

Initial target is local Linux with a restricted user-scoped daemon socket. Windows/macOS implementation and interactive prompt integration require their own security validation; global hotkey activation precedes risky credential typing. File paths, host manifests and installation identity must be configurable, not developer-machine constants. Backups are portable, but secure rollback detection may depend on a nonportable last-seen local record; warn on divergence, never promise malicious rollback resistance.

## Current implementation (do not confuse with target)

At merged PR #5, root Rust and reference checks pass. The default binary fails closed; VLT1/JSON parser and crypto helpers are legacy prototypes, the native host and daemon still return mock data, and the v0.4.5 vault format, runtime operation engine, trusted E2E IPC and recovery are not implemented. See [evidence register](../roadmap/acceptance-register.md).

**Release blockers:** independent OPEN-01 combiner/commitment and OPEN-15 physical PRF review, canonical authenticated codec, runtime policy and negative tests, trusted prompt/client pairing, hardware-failure paths, recovery and restore validation.
